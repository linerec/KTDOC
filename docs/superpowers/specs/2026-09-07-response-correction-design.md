# 수강신청 과목 정정 — 설계

2026-09-07 · 상태: 구현 완료(feat/response-correction, 미커밋·미배포) · D1 0044 원격 적용·백필 완료 · 발단: 응답 #173(Aiden Jee)이 과목을 잘못 넣고 배정까지 끝난 뒤 "제대로 고치는 길"이 없다는 것을 확인함.

## 1. 지금 무엇이 없는가

- 응답의 답(과목 포함)을 고치는 화면·API가 없다. PATCH는 상태와 메모만 받는다.
- 재제출 장치는 있다(같은 신청서·이메일·학생 이름이면 옛 응답이 `is_latest=0`). 그러나
  - `supersedes_response_id`는 어디서도 채우지 않아 "무엇을 대체했나"가 남지 않고,
  - 옛 응답이 만든 **배정은 그대로 살아 있으며**,
  - 재제출 접수 메일이 "재제출"이라는 사실도, 무엇이 바뀌었는지도 말하지 않는다.
- 배정 해제(수업 화면)는 아무에게도 알리지 않는다. 배정 생성만 메일이 나간다.
- '취소' 상태로 내려도 배정은 남는다.
- 정정의 기록은 자유 메모뿐이다. 무엇에서 무엇으로 바뀌었는지 구조로 남지 않는다.

## 2. 원칙

1. **응답은 사람이 낸 기록이고, 정정은 그 위에 얹는 사건이다.** 원래 값은 지우지 않고 "누가·언제·무엇을·무엇으로" 사건으로 남긴다.
2. **"신청 과목 = 배정"이라는 등식은 한 함수가 지킨다.** 신청 화면에서 배정을 만드는 것도, 정정으로 배정을 바꾸는 것도, 취소로 배정을 거두는 것도 같은 `planEnrollmentChanges`를 지난다. 신청서와 수업 화면 어느 쪽에서 봐도 어긋남이 보이게 한다.
3. **선생님은 한 자리에서 한 번 누른다.** 응답 상세의 '과목 정정' 하나가 답 수정·배정 조정·안내 메일·이력 기록을 함께 한다. 수업 화면으로 건너가 해제하고 돌아오는 절차를 없앤다.
4. **안내는 "바뀐 것"을 한 통으로.** 해제 메일 뒤에 등록 메일이 오면 실수처럼 읽힌다. 빠진 수업과 새 수업을 한 통에 적는다. 학비는 적지 않는다(신청자에게 학비표를 보이지 않는 기존 규칙).
5. **신청자가 스스로 고치는 길은 재제출 하나로 둔다.** 배정 뒤 자율 변경은 정원·우선순위·학비에 걸리므로 운영진을 지난다. 다만 재제출이 무엇을 바꾸는지 시스템이 알고 말하게 한다.

## 3. 두 가지 정정 모델 비교

| | A. 정정 = 새 응답 | **B. 정정 = 같은 응답 + 사건 기록(권장)** |
|---|---|---|
| 접수번호 | 바뀐다(학부모에게 알려 준 0173이 무효) | 유지 |
| 신청 순서(삼고무·오고무 선착순) | 뒤로 밀린다 | 유지 |
| 동의 증빙 | 복사하면 "다시 서명한 척", 안 하면 새 응답에 동의가 없다 | 그대로(동의는 사람과 문안에 속하지 문항 답에 속하지 않는다) |
| 처리 이력 | 두 행에 갈라진다 | 한 줄기 |
| 기존 재제출 장치와의 관계 | 같은 장치 | 다른 장치(그러나 배정 조정·알림·diff는 공유) |

**결론**: 운영진 정정은 B, 신청자 재제출은 기존 A. 두 길은 §5의 같은 부품(diff·배정 계획·안내 메일)으로 합류한다.

## 4. 시나리오별 흐름

배정 전/후를 가르는 것은 응답 상태가 아니라 **이 응답 줄기에서 나온 배정이 있는가**다.

### S1. 배정 전, 운영진이 고친다 (전화·카톡으로 "잘못 골랐어요")
1. 응답 상세 → **과목 정정** → 모달: 과목 체크 목록(현재 선택 표시, 배타 규칙 적용, '수업 미연결' 배지, 학비표 참고 줄이 즉시 갱신).
2. 요약 칸이 자동으로 채워진다: `과목: K-드럼 앙상블 → 성인반`. 배정이 없으니 배정 줄은 비어 있다.
3. 사유(선택, 내부용) + "신청하신 분께 변경 확인 메일 보내기"(기본 켜짐).
4. 저장 → 답·과목 선택 갱신, `correction` 이력, 메일 `form.corrected`.

### S2. 배정 후, 운영진이 고친다 (#173이 여기)
1~3은 S1과 같고, 요약에 배정 줄이 붙는다:
`배정: K-드럼 앙상블(#59) 해제 · 성인반 새로 배정`.
해제 방식은 자동 판정된다 — 학기 시작 전이면 삭제, 시작 뒤면 '취소'로 내린다(§6).
4. 저장 → 답 갱신 → `planEnrollmentChanges` 실행 → `correction` 이력(배정 변화 포함) → 메일 `enrollment.changed` 한 통(빠진 수업·새 수업·일정).
'수업 미연결' 과목으로 바꾸면 요약이 "배정은 만들지 못합니다 — 신청서 편집에서 수업을 연결한 뒤 '배정 맞추기'"라고 미리 말한다.

### S3. 신청자가 같은 신청서를 다시 낸다
1. `/f/[slug]`에 로그인 상태로 들어오면 최신 응답이 있을 때 안내 띠: "9/5에 접수된 신청(과목 A, B)이 있습니다. 다시 내시면 그 신청을 대체합니다."
2. 제출 시 옛 응답을 `is_latest=0`으로 내리는 자리에서 **`supersedes_response_id`를 채운다**(지금은 비어 있다).
3. 접수 메일(`form.submitted`)이 재제출임을 말한다: 신청자에게 "이전 신청을 대체했습니다 · 바뀐 것: 과목 A → C", 학원에는 "재제출 — 이전 #173(배정 완료) · 바뀐 것: …". 학원 쪽은 기본 켜짐 — 배정을 손봐야 하는 신호이기 때문이다.
4. 목록에서 새 응답에 '재제출' 배지 + 상세 상단에 "이전 응답 #173 대체 · 바뀐 것: …". 옛 응답 상세 상단에는 "#180으로 대체됨" 띠.
5. 선생님이 새 응답에서 **수업에 넣기**를 누르면 `planEnrollmentChanges`가 옛 줄기의 배정과 비교해 더할 것·거둘 것을 함께 처리한다. 메일은 배정 이력이 있으면 `enrollment.changed`, 없으면 지금처럼 `enrollment.created`.

### S4. 취소(과목 전부 빼기)
정정 모달에서 과목을 0개로 만들면 저장하지 않고 "취소는 '다르게 처리하기 → 취소'에서" 안내. '취소'로 내릴 때 배정이 있으면 "배정 N개도 함께 거둡니다" 체크(기본 켜짐) → 같은 계획 함수 → 메일 `enrollment.changed`(빠진 수업만).

### S5. 어긋남이 이미 생긴 경우 (누군가 수업 화면에서 해제했거나 부분 실패)
응답 상세는 항상 "신청 과목 ↔ 이 줄기의 배정"을 비교한다. 배정 완료 상태에서 어긋나면 경고 띠 + **배정 맞추기** 버튼. 정정 저장이 중간에 실패해도 같은 버튼으로 이어서 맞춘다(계획이 멱등이라 여러 번 눌러도 안전).

## 5. 부품

### 5.1 순수 로직 `lib/forms/correction.ts` (시험 있음)
- `applySubjectCorrection(schema, answers, questionKey, nextOptionKeys)` → 새 answers. 배타 선택지(`optionGroups`)·필수 규칙을 `validateAnswers`로 같이 검사.
- `diffSelections(prev, next)` → `{ added, removed, kept }` (키+라벨). 재제출 메일·정정 요약·이력이 모두 이것을 쓴다.
- `planEnrollmentChanges({ selections, chainEnrollments, programs, today })` →
  `{ add: [...], remove: [{ enrollmentId, mode: 'delete' | 'cancel' }], unlinked: [...] }`.
  **이 줄기가 만든 배정만 건드린다.** 운영진이 수업 화면에서 직접 넣거나 취소한 배정(source가 다른 것)은 그대로 둔다. 기존 promote의 "취소로 내려 둔 것은 되살리지 않는다" 규칙은 "남의 결정은 건드리지 않는다"로 일반화된다 — 자기 줄기가 취소한 것은 다시 고르면 되살린다.

### 5.2 데이터 (D1 0044)
- `program_enrollments.source_response_id INTEGER NULL` + 인덱스. 기존 행은 note의 `신청서 접수 #N`에서 채운다(백필 스크립트).
- `form_response_notes.payload_json TEXT NULL`. `kind`에 `'correction'` 추가.
  payload: `{ questionKey, from: [{key,label}], to: [...], schemaVersion: {from,to}, enrollments: [{programId,title,action:'added'|'deleted'|'cancelled'|'revived'}], mailed: boolean, reason }`.
- 응답 자체에는 새 컬럼이 없다. "정정됨"은 `correction` 이력의 존재로 안다.

### 5.3 문안 버전
정정은 **현재 신청서 문안**의 선택지로 고른다(옛 버전에 없던 과목으로 옮기는 일이 실제로 있다). 저장 시 `form_schema_version`을 현재로 올리고 이력 payload에 `v3 → v5`를 남긴다. 다른 문항의 답은 손대지 않는다. 답변 화면 문구 "신청하신 분이 실제로 본 문안 그대로"는 정정 이력이 있으면 "정정됨 — 원래 값은 이력 참조"로 바뀐다.

### 5.4 API
- `POST /api/admin/forms/[id]/responses/[rid]/correct` `{ questionKey, optionKeys, reason?, notify: boolean }`
  순서: 검증 → answers/선택 갱신 → 배정 계획 실행 → 이력(payload) → 메일. D1에 트랜잭션이 없으므로 각 단계가 멱등이고, 실패는 응답에 단계명을 담아 돌려주며 화면은 S5의 '배정 맞추기'로 잇는다.
- `POST …/reconcile` — S5 버튼. 계획 실행 + 이력만.
- `promote`는 계획 함수를 쓰도록 바꾼다(동작은 기존과 같되 옛 줄기 배정을 거둔다).
- `PATCH`(상태)에 `reconcileEnrollments: boolean` 추가 — 취소 시.
- 공개 `submit`·대리 입력 `responses`: `supersedes_response_id` 채우기 + 접수 메일에 diff.

### 5.5 화면
- `ResponseActions`: '수업에 넣기' 옆에 **과목 정정** 버튼(2차 강조). 모달은 위 S1/S2 요약을 저장 전에 보여 준다.
- 상세 '신청 과목' 카드: 정정 이력이 있으면 "9/7 정정: A → B (owenkdev)" 한 줄. '답변' 카드: 정정된 문항에 '정정됨' 배지와 원래 값.
- 상단 띠: 대체됨/대체함, 어긋남 경고.
- 목록: '재제출'·'정정' 작은 배지.
- 내 신청 내역(신청자): 최신 과목 + "9/7 과목 변경: A → B"(사유는 보이지 않음).
- `/f/[slug]`: 기존 접수 안내 띠(S3-1).
- 수업 화면 수강생 목록: note에 "정정 #173 (9/7)". 해제 버튼은 그대로 두되, 신청서에서 온 배정을 해제할 때 "응답 #173과 어긋나게 됩니다 — 신청 화면에서 정정하는 편이 기록이 남습니다" 확인 문구.

### 5.6 알림 매트릭스 (메일. 푸시는 §8)

| 사건 | 학생 | 학부모(자동 동봉) | 학원/선생님 |
|---|---|---|---|
| S1 정정(배정 전) | `form.corrected`: "신청 과목이 A에서 B로 변경되었습니다" | 같은 메일 | 이력만. staff 메일 기본 꺼짐(본인이 한 일) |
| S2 정정(배정 후) | `enrollment.changed`: 빠진 수업 / 새 수업 / 일정 | 같은 메일 | 이력만. staff 기본 꺼짐 |
| S3 재제출 | `form.submitted`(재제출·diff 명시) | 같은 메일 | `form.submitted` staff본에 diff + 이전 응답 상태. **기본 켜짐** |
| S3 후 배정 | `enrollment.changed` 또는 `created` | 같은 메일 | 이력 |
| S4 취소 | `enrollment.changed`(빠진 수업만) | 같은 메일 | 이력 |
| 모달에서 "메일 보내기" 끔 | — | — | 이력에 `mailed:false` 기록(전화로 이미 설명한 경우) |

수신자 규칙은 기존 `notifyEvent` 그대로(원생 id → 보호자 자동 추가, 자기 메일 없는 원생은 보호자만). 모든 새 이벤트는 관리 콘솔 메일 설정에 저절로 나타난다.

## 6. 배정을 거두는 방식

- **삭제**: 이 줄기가 만들었고, 수업이 아직 시작 전(구조 일정의 학기 시작일이 오늘 이후이거나 없음). 잘못 고른 반이 수강생 명단에 '취소'로 영원히 남을 이유가 없다.
- **취소로 내림**: 수업이 시작된 뒤. 출석·사진·캘린더에 이미 흔적이 있을 수 있어 행을 남긴다. note에 정정 사유.
- 판정은 `planEnrollmentChanges` 안에 있고 모달 요약이 어느 쪽인지 미리 말한다.

## 7. 기록이 남는 자리 (한눈에)

| 무엇 | 어디 |
|---|---|
| 무엇이 무엇으로, 누가, 언제, 왜 | `form_response_notes(kind='correction', payload_json)` |
| 원래 답 | payload의 `from` (전체 스냅샷이 아니라 바뀐 문항만) |
| 배정에 미친 영향 | 같은 payload의 `enrollments[]` + `program_enrollments.note`/`source_response_id` |
| 안내가 나갔는가 | 기존 `mail` 이력 + payload `mailed` |
| 재제출 관계 | `supersedes_response_id` 양방향 표시 |
| 신청자가 보는 기록 | 내 신청 내역의 변경 줄(사유 제외) |

## 8. 범위 밖 (이번에 하지 않음)
- 신청자 셀프 과목 변경 버튼(요청함 모델). 재제출로 충분한지 한 학기 본 뒤 결정.
- 푸시 알림 연동. `notifyEvent`는 메일 전용이고 푸시는 수동 공지용 — 정정 한 건 때문에 알림 오케스트레이션을 넓히지 않는다.
- 정원·대기 명단 판정.
- 과목 외 문항의 정정(이름·학년 등). 같은 API에 `questionKey`를 열어 두되 화면은 과목만 낸다.

## 10. 순서 (구현 계획의 뼈대)
1. 마이그레이션 + 백필 + 순수 로직·시험
2. `promote`를 계획 함수로 이전(동작 회귀 없음 확인)
3. `correct`/`reconcile` API + 메일 이벤트·문안
4. 정정 모달 + 상세/목록 표시 + 어긋남 경고
5. 재제출 연결(`supersedes`)·접수 메일 diff·`/f/[slug]` 안내 띠
6. 취소 시 배정 회수
7. 내 신청 내역 표시, 문서(CLAUDE.md 신청서 절에 '정정' 항목 추가)

## 11. 더블체크 (2026-09-07, 세 축으로 다시 봄) — 본문에 반영된 수정

### 11.1 선생님의 수정 편의
- **들어가는 길을 둘로**: 응답 상세의 '과목 정정' 외에 **과목별 명단(반편성 화면)의 각 줄에서 바로 '정정'** — 잘못 들어간 학생을 발견하는 자리가 명단이기 때문이다. 링크는 상세로 가되 모달이 열린 채로 뜬다(`?correct=1`).
- 모달은 **저장 전에 세 가지를 다 보여 준다**: 바뀌는 과목, 바뀌는 배정(삭제/취소 어느 쪽인지), 안내가 가는 주소(신청서 주소·계정 주소·보호자 주소가 다를 수 있다 — 기존 '메일 보내기' 카드와 같은 방식).
- 사유는 선택. 저장 뒤 결과 문구는 정직하다: "과목 정정 완료 · 배정 1개 해제, 1개 추가 · 안내 메일 2통 발송" / 실패하면 어느 단계에서 멈췄고 무엇을 누르면 이어지는지.
- 수업 화면에서 신청서 유래 배정을 손대면 "신청 화면에서 정정하는 편이 기록이 남습니다"라고 한 번 묻는다. 막지는 않는다.

### 11.2 학부모 ↔ 학생 데이터가 꼬이지 않게
- **정정은 `student_user_id`만 본다.** 제출자(`submitted_by_user_id`, 학부모일 수 있다)는 건드리지도 배정하지도 않는다.
- **회원을 다시 연결한 뒤의 배정**: 배정 계획은 이 줄기의 배정 중 `user_id`가 현재 연결 회원과 다른 것을 "잘못된 사람에게 간 배정"으로 보고 거둔다(형제를 잘못 연결했다가 고친 경우). 어긋남 경고가 이 경우도 잡는다.
- **재제출 묶기 기준을 바꾼다**: 로그인 제출이면 `(신청서, student_user_id)`로 먼저 묶고, 없을 때만 지금의 `(이메일, 학생 이름)`. 같은 보호자 주소로 두 자녀를 내는 집에서 이름 표기가 조금 달라도 엉키지 않는다.
- **모달 머리에 누구 것인지 크게**: 학생 이름 · 연결된 회원(원생) · 제출자. 형제 응답을 열어 놓고 고치는 실수를 줄인다.
- 같은 원생의 **다른 최신 응답**이 이 신청서에 또 있으면 상세 상단에 경고("같은 원생의 응답 #N이 따로 있습니다").
- 동의 증빙은 정정으로 재동기화하지 않는다(동의는 그때 서명이고 정정과 무관).
- 신청자가 보는 '내 신청 내역'(보호자 화면에는 자녀 응답이 함께 보인다)에도 같은 변경 줄이 뜬다 — 운영진과 가정이 같은 기록을 본다.

### 11.3 사전 공지와 사후 공지
- **정정은 두 가지 방식**을 고른다:
  - **바로 적용** — 학부모·학생이 요청해서 고치는 경우. 적용 뒤 확인 안내 한 통.
  - **먼저 예고, 나중에 적용** — 학원 사정으로 옮기는 경우(반 통합, 시간 변경, 잘못 배정). 저장 시 "○월 ○일부터 A → B로 변경 예정" 예고 안내가 나가고 기록은 아직 바뀌지 않는다. 상세에 '예고된 정정' 카드가 남아 **[지금 적용] [철회]** 를 준다. 적용하면 사후 안내가 나간다. 자동 예약 실행은 두지 않는다(운영진이 그 날 누른다 — 사람이 마지막으로 확인한다).
- **안내 내용의 규격**(예고·확인 공통): 학생 이름 / 바뀌는 것(빠지는 수업·새 수업, 요일·시간) / 언제부터 / 어디서 확인하나('내 수업' 링크) / 문의처. **학비는 적지 않는다.**
- **채널**: 메일(원생 + 보호자 자동) + **앱 알림함**(푸시를 켠 기기에는 푸시도). 푸시를 켠 회원이 절반뿐이라 메일이 기본이고, 알림함은 로그인하면 남아 있다.
- **학원 대표 메일 사본은 기본 켜짐**(`enrollment.changed`·`form.corrected` 모두). 정정은 드물고 누군가는 봐야 한다. 관리 콘솔 메일 설정에서 끌 수 있다.
- 모달의 "안내 보내기"를 끄면 이력에 `mailed:false`가 남는다(전화로 이미 설명한 경우). 발송이 실패하면 결과 문구가 그대로 말하고, 오른쪽 '메일 보내기' 카드로 손으로 보낼 수 있다.
- 신청자 재제출의 사전 공지는 `/f/[slug]`의 안내 띠("다시 내시면 9/5 신청을 대체합니다"), 사후 공지는 접수 메일의 "이전 신청을 대체했습니다 · 바뀐 것" 줄.

### 11.4 선생님용 가이드
구현 뒤 관리 콘솔 안에 **'신청 내용 고치기' 안내 페이지**(`/admin/forms/guide`)를 둔다 — 대면 산출물은 사이트 페이지로(아티팩트·외부 문서 아님). 신청서 관리 화면 머리와 정정 모달 안에서 링크한다. 문서 구성: 언제 어느 버튼인가(표) → 바로 적용 vs 예고 → 저장 전에 확인할 세 가지 → 실수했을 때(되돌리기 = 한 번 더 정정) → 자주 묻는 것.
